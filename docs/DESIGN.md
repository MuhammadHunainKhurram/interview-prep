# Interview Prep — Design Doc (v1)

Status: **Draft — awaiting approval**
Last updated: 2026-10-24

A Chrome extension (Manifest V3) that tracks LeetCode/NeetCode progress, schedules
full re-solves with spaced repetition, and keeps a GitHub-style streak with rest days.
Primary goal: finish NeetCode 150, then NeetCode 250, without forgetting what was learned.

---

## 1. Decisions so far

## 2. Architecture

```
src/
  entrypoints/            # WXT entrypoints (thin: wire features together, no logic)
    background.ts         # service worker: sole writer of data, alarms, notifications
    popup/                # today's plan + streak summary
    dashboard/            # full page: Home, Problems, Reviews, Stats, Settings
    leetcode.content.tsx  # widget on leetcode.com/problems/*
    neetcode.content.tsx  # widget on neetcode.io/problems/*

  core/                   # pure TypeScript domain logic — no chrome.*, no React
    catalog/              # problem catalog, list membership, URL → problem resolution
    srs/                  # Scheduler interface + FSRS implementation
    planner/              # builds the daily plan
    streak/               # day status + streak computation
    calendar/             # "logical day" (2 AM rollover), rest-day rules
    stats/                # derived metrics

  data/
    schemas/              # Zod schemas = single source of truth for data shapes
    repositories/         # interfaces: AttemptRepo, CardRepo, SettingsRepo, RestDayRepo
    adapters/
      chrome-storage/     # v1 implementation
      supabase/           # future implementation (same interfaces)
    migrations/           # versioned, tested schema migrations

  features/               # one folder per feature; each owns its UI + hooks
    widget/  today/  streak-heatmap/  reviews/  rest-days/  stats/  settings/  backup/

  shared/
    messaging/            # typed, Zod-validated messages between content ↔ background
    config/               # reads and validates env vars at build time
    ui/                   # shared components, theme tokens
```

**Rules that keep new features easy to add:**
- `core/` is pure and fully unit-tested; it receives a `Clock` instead of calling `Date.now()`.
- UI never touches storage directly: it calls repositories through the background worker.
- A new feature = a new folder in `features/` (+ optional `core/` module). No edits to other features.
- Every stored record is validated by Zod on read and write; bad data fails loudly, not silently.

## 3. Data model

All records use UUIDs and `createdAt` / `updatedAt` (ISO strings), plus `deletedAt` for
soft deletes. That makes later sync with Supabase straightforward (last-write-wins per record).

**Problem** (static catalog bundled with the extension, not user data)
```
id              canonical slug (LeetCode slug)
title, difficulty
leetcodeSlug, neetcodeSlug   (both kept; either URL resolves to the same problem)
leetcodePremium boolean      (some NeetCode-free problems are premium on LeetCode)
category        roadmap section, e.g. "Arrays & Hashing"
lists           { blind75?, nc150?, nc250?, ncAll? } → { sectionOrder, orderInSection }
defaultPatterns string[]
```

**Attempt** (append-only history; the source of truth for streaks and stats)
```
id, problemId, site ("leetcode" | "neetcode")
outcome         "easy" | "solved" | "hints" | "failed"
patterns        string[]   (prefilled from category, editable)
notes           string     (plain text, max length enforced)
durationSec     number | null   (null = not timed)
logicalDay      "YYYY-MM-DD" (after applying 2 AM rollover)
isReview        boolean
completedAt
```

**ReviewCard** (one per problem you've attempted; FSRS state)
```
problemId, due, stability, difficulty, reps, lapses, state, lastReviewedAt
```

**Settings**
```
activeList, dailyGoal, minReviewsPerDay, reviewCap, maxIntervalDays,
restWeekdays[], adHocRestBudgetPerMonth, rolloverHour (2), theme,
reminder { enabled, time }
```

**RestDay** `{ logicalDay, kind: "weekly" | "adhoc" }`

**DaySnapshot** `{ logicalDay, goal, minReviews, plannedProblemIds[], isRest }`
Saved when a day's plan is first built. Past days are judged against their own snapshot,
so changing settings never rewrites your streak history.

**TimerState** `{ problemId, startedAt | null, accumulatedMs, status: "idle" | "running" | "paused" }`
Stored as timestamps rather than a ticking counter, so it survives page reloads, tab
switches and the background worker restarting.

**Meta** `{ schemaVersion }` → drives migrations.

## 4. Spaced repetition

- FSRS with target retention 0.9 and `maximum_interval = maxIntervalDays` (default 365).
- Four outcome buttons, each mapped to an FSRS rating and a color:

  | Button | Color | FSRS rating | Effect on next review |
  |---|---|---|---|
  | Solved easily | Blue | Easy | Longest gap |
  | Solved | Green | Good | Normal growth |
  | Needed hints | Yellow | Hard | Shorter gap |
  | Didn't solve | Red | Again | Comes back soon (about 1 day) |

  Colors always come with a text label too, so the meaning never depends on color alone.
- A successful re-solve grows the interval; a failure shrinks it. The more often you
  solve a problem, the longer the gap before the next review.
- If a due date falls on a rest day, it moves to the next active day.
- Off-plan solves of a problem that has a card still update the card.
- Only the **first** attempt on a problem per logical day updates its card. Later attempts
  that day are still saved in history but don't change the schedule, so re-solving
  something you just looked up can't inflate its interval.

## 5. Daily planner

For logical day D (rest days get no plan):
1. **Reviews:** cards due on or before D, most overdue first, up to `reviewCap`.
   If none are due but a card is due within 3 days, pull it in early so the day still
   includes a review. Before you've solved anything, review slots become new problems.
2. **New:** fill the rest of `dailyGoal` with the next unsolved problems from the active
   list, in roadmap order.
3. Overdue backlog beyond `reviewCap` rolls forward, so a vacation doesn't produce a
   30-review day.

Counting toward the goal: the goal is met when the number of **distinct problems**
attempted that day (any outcome) ≥ the day's goal, including at least `minReviews` reviews
when reviews were available.

## 6. Streak and rest days

- Each day has a status: `goal-met` | `partial` | `missed` | `rest` | `today`.
- Streak = consecutive `goal-met` days going back from today; `rest` days are skipped
  (they don't break the streak or add to it). Today doesn't break the streak until it ends.
- Ad-hoc rest days: mark today, a future day, or **yesterday** (a grace option), limited
  by the monthly budget (default 4).
- Heatmap: 52-week grid, shaded by the number of problems done; rest days shown differently.

## 7a. Visual design

Inspired by Duolingo's web UI: clean, friendly, easy to read at a glance. Not goofy:
no mascots, no confetti storms, no sounds.
- Rounded corners, chunky buttons with a subtle bottom-border "press" effect
- A rounded sans-serif font (Nunito), **bundled locally** (no remote font loading)
- Big, clear progress bars per list and per roadmap section
- One main action per screen ("Start today's plan"), lots of white space
- Dark theme by default; color tokens defined once and shared by every surface
- Accessible: WCAG AA contrast, keyboard navigable, visible focus rings, respects
  "reduce motion"

## 7. On-page widget

- Rendered inside a **Shadow DOM** so the host page's CSS and scripts can't affect it.
- Collapsed: a small pill in the top-right (timer + status dot). Expanded: a dropdown with
  - problem title and badges (list, difficulty, "Review" / "New")
  - timer: start / pause / reset (starts only when you click Start)
  - outcome: Solved easily · Solved · Needed hints · Didn't solve. Clicking one stops the
    timer and saves the attempt, then shows a 5-second **Undo**.
  - patterns (prefilled from the NeetCode category, editable)
  - notes (plain text)
  - last solved date, attempt count, next review date
- Handles single-page-app navigation (LeetCode changes the URL without reloading the page).
- Shortcut (default `Alt+Shift+S`, can be changed in `chrome://extensions/shortcuts`) opens it.

## 8. Security and configuration

- **Permissions:** `storage`, `unlimitedStorage`, `alarms`, `notifications`.
  **Host permissions:** only `https://leetcode.com/problems/*` and `https://neetcode.io/problems/*`.
- No remote code; the default Manifest V3 content security policy; no `innerHTML` or
  `dangerouslySetInnerHTML`. Notes are always displayed as plain text.
- The background worker accepts messages only from this extension (`sender.id` check),
  and validates each one with Zod.
- Backup import is validated with Zod and migrated before it is written; you see a preview
  before it replaces your data.
- **Env vars:** `.env.example` is committed and `.env` is gitignored. Everything in an
  extension bundle is readable by anyone who has the extension, so only public values go
  there (for example, a Supabase URL and anon key, protected by row-level security).
  Never a service-role key or other secret. Config is validated with Zod at build time.
  ```
  WXT_STORAGE_BACKEND=local      # local | supabase (future)
  WXT_SUPABASE_URL=
  WXT_SUPABASE_ANON_KEY=
  ```
- Dependencies: pinned via lockfile, Dependabot, `npm audit` in CI.
- No analytics or telemetry. Data never leaves the browser in v1.

## 8a. Edge cases and validation

Limits are enforced in the **Zod schemas** (not just in the form), so they apply equally
to the Settings page, imported backups and messages between parts of the extension.
Invalid input shows an inline message and disables Save. It is never silently clamped.

| Setting | Allowed |
|---|---|
| Daily goal | whole number 1–20 |
| Min reviews per day | whole number 0 to the daily goal |
| Review cap | whole number from min reviews up to 50 |
| Weekly rest days | 0–6 weekdays (at least one active day per week) |
| Extra rest days per month | whole number 0–8 |
| Max review interval | 30–3650 days |
| Day rollover hour | 0–6 (12 AM–6 AM) |
| Reminder time | valid HH:MM |
| Notes | max 5,000 characters |

Rest days:
- An extra rest day can't be placed on a weekly rest day (no double counting) or on a day
  that already has attempts. The monthly budget is checked against that specific month,
  so 28-, 30- and 31-day months and leap years all work.
- Allowed only for yesterday, today or future days, and at most 90 days ahead.
- Changing weekly rest days applies from today forward; past days keep their snapshot.

Time:
- `logicalDay` is computed once, when the attempt is saved, and never recomputed. Daylight
  saving changes, timezone changes while traveling and settings changes can't move past
  attempts.
- Attempts whose time is in the future (e.g. the system clock was wrong) are kept, but
  ignored by streak logic until that day arrives.

Widget and attempts:
- Outcome buttons are disabled while a save is in progress, so a double-click can't
  create two attempts. The 5-second Undo covers accidental clicks. Attempts can also be
  edited or deleted later from History.
- The same problem open in two tabs shares one timer, owned by the background worker.
- Saving without starting the timer records the attempt as "not timed". It's not an error.
- A timer left running for more than 6 hours asks whether to keep or discard that time.
- Problem URLs not in the catalog become *unlisted*. Pages that aren't problem pages
  (contests, discussions, Explore) don't show the widget.
- Switching the active list never loses progress. A problem in several lists is one
  problem, so solving it once counts in all of them.

Data safety:
- If stored data fails validation, the app never wipes it. The bad data is set aside in
  quarantine, and you're offered an export of the raw data and a restore from a backup.
- Import: file size limit of 5 MB. Backups from a newer app version are refused (no
  downgrade). You see a preview, and a backup of your current data is taken before
  anything is replaced.
- The background worker keeps no state in memory; everything is read from storage, so a
  worker restart loses nothing.

## 9. Scope

**v1:** catalog (4 lists + mapping between the two sites), widget, timer, manual solve
recording, notes, FSRS, daily planner, streak heatmap, rest days, popup, dashboard (Home,
Problems, Reviews, Stats, Settings), reminder, shortcut, JSON export/import, dark/light theme.

**v2+ candidates:** import NeetCode checkmarks, capture submitted code from the editor,
auto-detect "Accepted" submissions, Supabase sync across devices, AI hints and summaries.

## 10. Quality

- Unit tests (Vitest) for all of `core/`, using a fake clock: rollover edge cases, rest days,
  streak breaks, review capping, FSRS mapping.
- Migration tests: every schema version's fixtures upgrade cleanly.
- E2E (Playwright) loads the unpacked extension; covers widget → attempt → plan → streak.
- CI: typecheck, lint, test, build on every push.
